目前架構

目前是單一 Next.js + Payload 應用。三個 Part 產生器直接呼叫外部來源、上傳 Media，並各自 find/update 同一筆 DailyReport。入口可由 API route 或本地 node 腳本觸發；MongoDB 儲存報告與 Media metadata，本地檔案夾或 S3 儲存圖片。

責任分離

Concern
Generator 是 orchestration、資料存取與來源邏輯的混合體

part1/2/3 直接呼叫 Payload、外部 fetch、Playwright 與 media upload；因此來源變更會同時影響 domain 狀態與 persistence。

凝聚與耦合

Risk
三個 writer 共用一筆可變的 aggregate

每個 Part 都讀取舊資料後整筆 update；重跑時可能把其他 Part 的 relation 寫成 null。這是連鎖失敗與日期錯置的主要放大器。

分層架構

Concern
沒有明確 application/domain/infrastructure 邊界

source fetchers、圖片驗證、Payload upload、status policy 分散在同一層，難以替換 UDN adapter 或模擬依賴。

Ports and Adapters

Risk
外部來源沒有統一契約與可替換 fallback

經濟日報的 public endpoint 和 SSO fallback 是特例邏輯；沒有把 403、登入超時、日期不可用表達成可分類的 adapter result。

擴展性

Concern
長時間 Playwright 與外部下載在同步 runner 內串行

單次作業容易超時，也沒有 queue、lease、backpressure 或 per-source concurrency 控制。

可觀測性

Concern
有 errorLogs，但缺少 attempt、provider、HTTP status、duration 與 artifact identity

目前可知道 403，卻難以回答哪個 URL、哪次重試、哪個檔案已寫入；不利於判斷可安全重跑的範圍。

可靠性

Risk
單一來源失敗使整份報告 failed

DailyReports.status 只有一個全域狀態，share package 又把所有 media 當作 ready gate；P2 403 因此污染 P1/P3 的可用性。

韌性

Concern
重試不是按來源分類，且沒有 circuit breaker 或 stale policy

對持續 403 的來源重試不會提高成功率，反而延長整批作業；應該快速失敗、標記 degraded，保留可用 Part。

資料架構

Risk
Media metadata 沒有 domain-level date/source/page identity

上傳 filename 和 alt 是字串，沒有唯一鍵或 validator 確保 reportDate、pageCode、來源與內容一致；曾出現 alt 9/21、filename 9/22。

可操作性

Concern
沒有單一 run manifest 與可重跑命令

人工需要知道先跑哪個 Part、哪些檔案可保留、哪些錯誤可忽略；缺少 idempotent run ID 與 repair mode。

部署架構

Concern
本地 media 與正式站 storage 行為不一致

本地檔案可讀不代表正式站 API 可讀；部署驗證應在 package level 檢查所有 artifact HTTP 可下載。

API 架構

Concern
API 回傳以整體 status 表達部分成功

呼叫者無法只重跑失敗的 source；應回傳 per-part/per-artifact status、可重跑 scopes 與 readiness。

建議架構

Recommended Component Diagram

graph LR Trigger["Manual / scheduled trigger"] --> Run["ReportRun orchestrator"] Run --> Jobs["Independent Part jobs"] Jobs --> Ports["Source adapter ports"] Ports --> Adapters["BlockTempo / CTEE / UDN / Market adapters"] Jobs --> Validator["Artifact + date + content validator"] Validator --> Repo["Report repository"] Validator --> MediaRepo["Media repository"] Repo --> DB[("MongoDB")] MediaRepo --> Store["S3 or local media"] Run --> Manifest["Run manifest + per-artifact state"]

Recommended Sequence

sequenceDiagram participant R as ReportRun participant J as Part job participant A as Source adapter participant V as Validator participant S as Storage R->>J: start independent part with runId J->>A: fetch with timeout and bounded retry A-->>J: success or classified failure J->>V: validate sourceDate, pageCode, hash, dimensions V-->>J: artifact accepted or rejected J->>S: idempotent upsert artifact J-->>R: per-artifact result R->>R: aggregate partial / ready / degraded
  1. 先拆狀態模型。保留 DailyReport.status 作為聚合狀態，新增每個 Part 與每個 artifact 的 state（pending、generated、degraded、failed），禁止 Part writer 用 null 覆蓋其他 Part。
  2. 建立 run manifest。以 reportDate + runId + partId + artifactKey 做唯一鍵；重跑只 upsert 指定 artifact，並保留 attempt、provider、URL、HTTP status、hash、尺寸與時間。
  3. 把來源抽成 adapters。每個 adapter 回傳統一的 Result，不讓 403、SSO timeout、日期不存在直接穿透到 report writer；403 應快速失敗並進入 degraded policy。
  4. 加強 media invariant。filename、alt、sourceDate、pageCode 必須由同一個 artifact key 產生；上傳前驗證圖片尺寸、hash 非重複、可解析日期，Payload relation 只接受已驗證 artifact。
  5. 改成獨立 job 與可安全重跑。P1/P2/P3 可平行或分批執行；P2 失敗不阻止 P1/P3 產生，package API 只在必要 artifact 全部 ready 時回報 ready。
  6. 加入來源健康策略。連續 403 開 circuit，暫停無效重試；可選 stale-but-labelled fallback，但不得把別日圖片偽裝成今天。
  7. 驗證門檻分兩層。單元／整合測試驗證 adapter 與 state merge；部署後 verifier 驗證 package readiness、每個 media URL HTTP 200、日期與 artifact key 一致。

Migration notes

第一階段先新增 immutable artifact key、per-part state 與 merge writer，並保留現有 API。第二階段把 Economic Daily、CTEE、market sources 改成 adapters，加入 403 circuit 與 contract tests。第三階段再把 runner 移到 queue/worker，最後把正式站部署 verifier 接到發布流程。這個順序可先消除資料覆蓋與錯誤污染，再處理外部來源本身的不穩定。
